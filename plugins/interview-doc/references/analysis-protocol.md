# 분석 규약

주석과 심층분석의 깊이를 지키기 위한 규칙. 이 문서를 지키면 인터뷰 유형이 달라져도 밀도가 유지된다.

---

## 1. 주석(note)의 형태

**관찰 → 해석 → 함의.** 세 층이 다 있어야 주석이다. 관찰만 있으면 자막이고, 해석만 있으면 근거 없는 주장이다.

```
좋음   입력 필드가 곧 기능 선언이다. 이미지 박스 하나만 있는 화면은 "이건 이미지를
       읽는 도구"라고 말하지만, 마케팅은 "문제를 만드는 도구"라고 말한다.
       사용자는 두 선언 사이에서 스크린샷이라는 자해적 우회로를 발명했다.
       └ 관찰(화면 구성) → 해석(두 선언의 충돌) → 함의(사용자가 비용을 떠안음)

나쁨   사용자가 이미지만 업로드할 수 있어서 불편함을 느끼고 있다.
       └ 발화를 다시 말했을 뿐. 새로 알게 된 것이 없다
```

길이는 2~4문장. 그보다 짧으면 대개 요약에 그친 것이고, 길면 심층분석으로 올려야 한다.

### 밀도

- **맞장구(`bc`)에는 절대 달지 않는다.** 여기가 밀도 차이의 출발점이다
- 실질 발화의 대부분에는 달아도 좋다. 다만 **무게를 차등**한다 — 어떤 주석은 한 문장, 어떤 주석은 네 문장
- 모든 주석이 같은 길이·같은 톤이면 중요도 신호가 사라진다

---

## 2. 심층분석(analysis)의 형태

챕터의 **종합 판단**이다. 주석이 즉각 반응이라면 이쪽은 물러서서 내리는 결론.

- **전체 챕터의 절반 정도에만.** 모든 챕터에 달면 무게중심이 사라진다
- 제목은 **판단문**이어야 한다. 주제 나열이 아니다
  - 좋음: "온보딩은 증상이고, 원인은 제품 정체성과 마케팅 약속의 카테고리 불일치다"
  - 나쁨: "온보딩 문제에 대하여"
- 근거 → 해석 → 함의 → (선택) `verdict` 블록으로 결론
- `verdict`는 "그래서 무엇을 할 것인가/하지 않을 것인가"까지 간다

## 3. 실패 모드

### 요약병

발화를 다시 말하는 것. **테스트: 이 주석을 지우면 독자가 잃는 것이 있는가?** 없으면 지운다.

### 요청 = 문제 착각

사용자가 "도움말 영상이 필요하다"고 하면 도움말 영상이 해법이라고 적는 것. 요청은 **사용자가 자기 쪽 노력으로 격차를 메우려는 우회책**인 경우가 많다.

**항상 물어라: 이 요청이 우회하려는 진짜 결함은 무엇인가?**

```
요청           "도움말 영상을 만들어 달라"
우회 대상      제품이 무엇인지 화면에서 알 수 없다
진짜 결함      마케팅 약속과 실제 기능의 카테고리 불일치
```

### 균등 주석

모든 대목을 똑같은 무게로 다루는 것. 인터뷰에는 무게중심이 있다. 대개 3~5개 대목이 문서의 절반을 감당한다.

### 일반론

"사용자 경험 개선이 필요하다", "중요한 인사이트를 얻었다" — 이 인터뷰가 아니어도 성립하는 문장. `check.mjs`가 일부를 잡지만 전부는 못 잡는다.

**테스트: 이 문장에서 고유명사와 숫자를 빼도 말이 되는가?** 되면 일반론이다.

### 서사 정리벽

모순을 지워 깔끔하게 만드는 것. 사용자가 앞에서 "좋다"고 하고 뒤에서 "해지했다"고 하면, **그 모순 자체가 발견**이다. 둘 중 하나를 고르지 말고 둘을 나란히 놓는다.

### 팀 발화 무시

인터뷰어(우리 쪽)의 발화도 데이터다. 우리가 무엇을 놓쳤는지, 어떤 답변이 사용자의 오해를 굳혔는지가 거기 있다. 레퍼런스 사례에서 가장 날카로운 주석 두 개는 팀 발화에 달렸다.

---

## 4. 렌더 전 자문

1. 모든 주요 주장이 특정 발화로 추적되는가
2. 주석의 무게가 균등하지 않은가
3. 대조표의 축이 이 인터뷰에 맞게 정해졌는가 (다른 인터뷰에 그대로 써도 되는 축이면 잘못됐다)
4. 사용자가 말한 것과 우리가 판단한 것이 시각적으로 구분되는가
5. 모순이나 미확인 사항이 숨겨지지 않았는가 — 없으면 `followups`에 "미검증 가설"로 남긴다
6. 대화의 흐름(누가 꺼냈고 어디서 이어졌는지)이 챕터마다 드러나는가
